## En bref

**Un fournisseur externe est ponctuel par construction.** « Providers without it execute through start and do not accept subsequent messages » (`sa/types.ts:345-346`, à propos de `prepareContinuable`) ; un message vers un tel enfant échoue en `NOT_CONTINUABLE` (`sa/activation.ts:115-119`) et `SubagentStartRequest` n'a aucun champ de reprise (`sa/types.ts:136-183`). Forker `run.ts` ne rend donc pas Claude Code continuable : l'identifiant de session, le `resume` et les relances sont à porter par QRG.

**DSH refuse les questions humaines venant d'un agent délégué.** `ctx.userQuestions.ask` rejette tout agent qui n'est pas une racine vivante avec `DELEGATED_CALLER` et demande de placer la question dans le résultat final de l'enfant (`uq/index.ts:131-144`) ; la note DSH écarte le relais faute de « durable request identity, routing, cancellation, and timeout semantics » (`note-ps:76`). Le relais `qrg-ask` ne peut afficher une question qu'au nom de la session racine : c'est un contournement de la politique DSH, à faire valider puis à proposer dans la discussion DSH.

**Le journal de session n'accepte pas d'événements libres.** Un type inconnu sans marque `ignorable` rend le journal illisible (`packages/core/session/src/known-event-types.ts:8-21`) et `Session.append` ne pose jamais cette marque (`packages/core/session/src/index.ts:798-827`). Dans l'API lue, la seule voie est `appendPluginRecord`, « experimental plugin record » hors de la surface du modèle, conservé « on a best-effort basis » lors des migrations, que DSH réserve dans son propre dépôt à ses paquets expérimentaux (`index.ts:468-498`), et absent au tag. Décisions, questions et usage doivent vivre dans un stockage QRG, le journal n'en gardant qu'un miroir.

**La configuration n'est pas verrouillable et l'échec d'un plugin n'est pas fatal.** Les couches de l'utilisateur passent après le profil et remplacent des lignes entières (`boot/profile-context.ts:74-84`), un bundle incompatible est sauté (`boot/profile.ts:732-733`) et seules huit entrées sont requises au démarrage (`boot/index.ts:944-960`). S-01 tel qu'écrit n'est pas atteignable par un schéma ; le refus fiable se fait à chaque délégation dans `qrg-router`.

**DSH n'émet aucune trace OpenTelemetry et envoie des données à DeepSeek par défaut.** Le paquet OTel de DSH n'embarque que le SDK de logs, sans SDK de traces (`packages/telemetry/otel/package.json:32-38`). Le modèle de tête par défaut est `deepseek-official` (`base.yml:90-94`) et chaque requête vers l'API officielle porte `dsh_session_log`, jusqu'à 8 Mio (`packages/session/session-log-deepseek/src/index.ts:1-6, :40-54`). Le profil `qrg` doit couper ces flux ; la décision revient au Security Officer.

Version recommandée : 0.2.1-alpha.4, épinglée (section « Version de DSH à cibler »).

## Profil `qrg`

**Forme.** Un profil est un répertoire `$DSH_HOME/profiles/<nom>` (`boot/profile.ts:36-40`) qui contient un `package.json` dont `dsh.profile.bundles` liste les bundles dans l'ordre, un `cordis.patch.yml` et un `pnpm-workspace.yaml` (`boot/profile.ts:262-281`). Un bundle est un paquet npm qui déclare `"dsh": {"bundle": {"patch": ...}}`, un chemin ou une liste de chemins (`boot/profile.ts:58-64` ; exemple `cc/package.json:34-36`). QRG livre un bundle dont le patch insère ses plugins et surcharge par `id` les lignes de la base.

**Création et installation.** Le CLI est le paquet `@deepseek-ai/dsh`, binaire `dsh` (`apps/cli/package.json:2, :14-16`). `dsh plugin --profile <nom> <arguments pnpm>` transmet la suite à pnpm dans le répertoire du profil (`apps/cli/src/args.ts:187-203`, usage `:155`, exemple `:99`), exige pnpm (`apps/cli/src/plugin.ts:98`) et accepte un nom npm, un chemin, une archive ou une source git comme `github:org/depot#sha` (`packages/boot/plugin-manager/src/install-spec.ts:15-30`). Un profil inconnu est créé au premier usage avec `@deepseek-ai/dsh-base` seul (`apps/cli/src/args.ts:194` ; `boot/profile.ts:212-213`), donc sans interface web. Ordre proposé, non exécuté : `dsh qrg --from-default-profile web`, qui copie le gabarit `web` (`dsh-base` et `dsh-web-app`, `apps/cli/src/args.ts:93-94` ; `boot/profile.ts:183-185`) puis démarre le profil, ensuite `npx -y @deepseek-ai/dsh@0.2.1-alpha.4 plugin --profile qrg add <bundle QRG>`. À master, `--from-default-profile` remplace un profil existant (« replace a custom profile with a fresh copy », `apps/cli/src/args.ts:169`) : ne pas le relancer sur un profil configuré.

**Couches et absence de verrou.** L'ordre d'application est : bundles, patch du profil, `$DSH_HOME/cordis.patch.yml`, chaque `--patch`, puis, si `DSH_TELEMETRY_DISABLED` est posé, la coupure de télémétrie (`boot/profile-context.ts:74-84` ; `publish.md:122-127`). Un patch remplace toute la `config` d'une ligne (`publish.md:131-133` ; `base.yml:6-10`). L'utilisateur peut donc rétablir tout ce que QRG retire, et la page Models comme l'éditeur de presets écrivent dans le patch du profil (`docs/user/guide/providers.md:50` ; `standard.yml:1-3`), ce qui y fige une copie des lignes du bundle.

**Compatibilité.** `engines.dsh` décide seul ; sinon toutes les dépendances pairs `@deepseek-ai/dsh*` doivent correspondre (`boot/plugin-compatibility.ts:55-80`). Au démarrage, un bundle incompatible ou illisible est sauté avec un message, sans arrêt (`boot/profile.ts:732-733, :751-767, :118-121`), alors que `publish.md:66` dit que le démarrage le « refuse ». Un DSH monté hors plage démarre donc le profil sans les lignes du bundle QRG. Les lignes de sécurité (modèle de tête, presets, coupure des flux, permissions) doivent aussi figurer dans le `cordis.patch.yml` du profil, qui s'applique toujours.

**AI Gateway.** Le fournisseur générique `@deepseek-ai/dsh-llm-pi-ai` est monté sans route (`base.yml:128-136`). Ses routes sont les clés du dictionnaire `providers` ; chaque clé est la valeur à passer dans `agentOptions.provider` (`packages/llm/llm-pi-ai/src/config.ts:185-189, :352-354`), avec `apiKeyEnv`, `api`, `baseURL`, `models`, `compat`, `headers`, `timeoutMs` (`config.ts:326-349`) et `api` parmi `openai-completions`, `openai-responses`, `anthropic-messages` (`packages/llm/llm-pi-ai/src/provider.ts:47-51`). Exemple de ligne : `docs/user/guide/providers.md:63-66`. Le modèle de tête vient de `agent-default-model` (`base.yml:90-94`) : le profil le pointe sur une route de la gateway, et le waterfall `agent/request` permet en plus de remplacer la route à chaque requête (`packages/core/agent/src/runtime-types.ts:321-337`).

**Outils visibles du modèle de tête.** Le registre de sous-agents et ses fournisseurs restent au niveau hôte ; un preset choisit seulement les outils de délégation que voit son agent (`web.yml:545-568`). Un preset est une ligne `@deepseek-ai/dsh-agent-preset` `{id, order, plugins}` (`packages/preset/agent-preset/src/index.ts:12-29`), `standard` par défaut (`web.yml:579-586`). `standard` et `ptc` contiennent un groupe `delegation` (sous-agents, fork, workflow, contrôle des enfants : `standard.yml:83-109` ; `packages/bundle/web-app/presets/ptc.patch.yml:83-100`). Pour que `route_and_delegate` soit le seul chemin, le profil remplace ces groupes par les outils QRG ; l'utilisateur peut toutefois changer de preset (`select`, `packages/preset/agent-preset-registry/src/index.ts:348-349`) ou l'éditer.

**Permissions.** Le mode `full` n'existe pas ; les modes sont `read-only`, `workspace-write` et `danger-full-access` (`packages/sandbox/sandbox-policy/src/session-mode.ts:42`). Le mode de base et la politique d'approbation se lisent dans `DSH_PERMISSION_MODE` (`base.yml:246, :262`), les presets de permission offrent `danger-full-access` avec approbation `never` (`base.yml:264-276`) et une session peut changer de mode par un événement `sandbox/mode` (`session-mode.ts:44-46`). Un enfant natif hérite du preset `auto` ou `danger-full-access` de son parent, avec une approbation fixée à `never` (`sa/child-agent.ts:220-255`). Le profil peut réécrire les lignes `sandbox-policy`, `approval` et `permission` en valeurs littérales sans `danger-full-access`, sans empêcher une couche ultérieure de les rétablir.

**S-01.** Seules `agent-loop`, `webserver`, `web-runtime`, `modules`, `connection`, `headless-runner`, `acp` et `sdk-jsonrpc-server` sont requises ; l'échec des autres entrées produit un avertissement (`boot/index.ts:944-960, :1137-1167`). Une exception dans l'`apply` d'un plugin QRG ne bloque donc rien. Deux pistes non testées : une expression `disabled: !!js` qui lève une exception sur une entrée requise fait échouer le démarrage (« A throwing disabled expression is an entry failure », `boot/index.ts:1144`), et le service `appExit` demande un arrêt borné (`packages/boot/cmdline/src/index.ts:35-41, :87`). La garantie fiable est un refus dans `qrg-router` à chaque délégation, en lisant `permissionPresets.current(session)` et `sandboxPolicy.overrideOf(session)` comme DSH le fait (`sa/child-agent.ts:248-255`).

**Secrets.** Les clés se désignent par `apiKeyEnv` et se résolvent à chaque requête par `ctx.credentials` : la configuration ne porte que des noms de variables, les valeurs restent chez le fournisseur d'identifiants (`base.yml:128-131` ; `packages/credentials/credentials/src/index.ts:1-9`). Un courtier comme CredOS se brancherait en étendant `CredentialProvider`, qui fournit le service `credentials` (`credentials/src/index.ts:171-174`) ; le remplacement de `credentials-local` reste à tester. Le fournisseur local lit `$DSH_HOME/.credentials.yaml`, puis l'environnement, puis `.env` du répertoire courant, puis `$DSH_HOME/.env` (`packages/credentials/credentials-local/src/index.ts:1-16`) ; au tag l'environnement passe en premier (tag: `:6`). Les patchs acceptent `!!js`, évalué par `new Function` et `eval` (`vendor/loader/src/config/utils.ts:5-9`) : un profil est du code, à auditer comme un plugin.

**Flux sortants par défaut.** La base exporte la télémétrie de session après un retour explicite de l'utilisateur vers `https://dsh-otel-collector.deepseeksvc.com/v1/logs`, avec un identifiant anonyme (`base.yml:202-232`) ; elle ajoute `dsh_session_log` (activé par défaut) et `dsh_plugin_packages` aux requêtes vers l'API officielle DeepSeek (`packages/session/session-log-deepseek/src/index.ts:184-197` ; `packages/llm/plugin-package-inventory-deepseek/src/index.ts:1-6, :199-213`) et confie la recherche web à `deepseek-official` (`base.yml:465-469`). `DSH_TELEMETRY_DISABLED` non vide coupe la télémétrie en désactivant sa ligne par `id` (`boot/profile-context.ts:41-55`) ; le même patch `disabled: true`, posé par le profil, vaut pour `session-log-deepseek`, `plugin-package-inventory-deepseek`, `llm-deepseek` et `llm-deepseek-account` (`base.yml:43-44, :85-86, :518-522`), et la recherche web demande un autre `searchProvider` ou la désactivation de la ligne `web` (`base.yml:465-469`). Effet sur les lignes dépendantes à tester ; décision à soumettre au Security Officer.

**Au tag.** Même format de profil et de bundle, liste comprise (tag: `boot/profile.ts:58-61`), même commande `plugin` (tag: `apps/cli/src/args.ts:99, :187-190`) ; `engines.dsh` y est ignoré, seuls les pairs comptent (tag: `boot/plugin-compatibility.ts:68, :75-77`) ; `--from-default-profile` n'y faisait qu'initialiser un nouveau profil (tag: `apps/cli/src/args.ts:169`) ; presets déjà présents.

## `qrg-router`

**Forme.** Un plugin fonction exporte `name`, `inject`, `Config` et `apply`, sans export par défaut ; mélanger les deux formes fait ignorer au Loader les exports nommés du plugin (`packages/AGENTS.md:5`). Cordis est vendoré en 4.0.5-alpha.2 (`vendor/cordis/package.json:2-4` ; 4.0.4 au tag). Comme le registre de sous-agents vit au niveau hôte (`web.yml:545-550`), `qrg-router` se scinde en une ligne hôte (moteur de décision, registre, file d'attente, appels à `ctx.subagents`) et une ligne d'outils insérée dans les presets, sur le modèle de `tool-subagent` (`standard.yml:93-98`).

**Outils et commandes.** `defineTool` puis `ctx.tools.register`, global ou limité à l'agent appelant (modèle : `packages/interaction/tool-ask-user/src/index.ts:33-118` ; `packages/core/tools/src/index.ts:1065-1096`), pour `route_and_delegate` et `explain_route`. `ctx.commands.register` pour `/qrg-stats` (`packages/interaction/commands/src/index.ts:60-78, :280-292`, nom conforme à `/^[a-z][a-z0-9_-]*$/u`, `:32`).

**Délégation.** `ctx.subagents.startActivation({provider, label, childId?, request, signal, delivery})` (`sa/index.ts:269-284` ; `sa/types.ts:31-44`). `request` porte `prompt`, `parent`, `cwd`, `agentPreset`, `agentOptions` (`provider`, `model`, `reasoningEffort`, `maxTokens`), `outputSchema` et `maxDepth` (`sa/types.ts:136-183` ; `packages/core/agent/src/runtime-types.ts:26-35`). `parent` doit être l'agent vivant exact (`sa/index.ts:277-279`), donc l'agent qui appelle l'outil. « Parent delivery notifies the model; caller delivery only returns the result » (`sa/types.ts:42`). `cwd` place chaque enfant dans son worktree ou son export (`sa/types.ts:137` ; `sa/manager.ts:524-529`). Le service expérimental `ctx.worktrees.create(agent, {name?, from?})`, à master seulement, crée branche et checkout sous `.agents/worktrees/` puis y déplace le répertoire de l'agent passé (`packages/experimental/worktree/src/index.ts:60, :107, :170`) : il ne prépare rien pour un enfant à venir et Claude Code n'a pas d'agent DSH, donc QRG crée ses worktrees lui-même, en s'inspirant au besoin de ce code. `agentPreset` remplace l'ancien `persona`, refusé par `tool-subagent` (`packages/subagent/tool-subagent/src/index.ts:147-151`) et accepté seulement par `spawn` (`packages/subagent/subagent-spawn-in-process/src/index.ts:39-44`) ; il sert à donner à l'enfant l'outil `ask_user` de QRG.

**Modèle explicite.** Sans option, un enfant prend la route de la dernière requête du parent et les options demandées passent par-dessus (`sa/child-agent.ts:60-85, :98-119`). Le modèle est figé dans le descripteur de l'enfant et réutilisé à la reprise à froid (`sa/manager.ts:390-401, :1368-1374`) : changer de modèle impose un nouvel enfant.

**Itération.** Pour un enfant natif, `sendMessage(sender, targetId, content, {signal})` part de l'agent parent vivant (`sa/index.ts:296-317`), et la méthode distante `prompt` permet déjà au navigateur d'écrire à un enfant continuable via son parent (`sa/index.ts:429-448`). Pour un enfant externe, aucune relance n'est possible (`NOT_CONTINUABLE`).

**Limites.** `maxActiveSubagents` vaut 8 et `maxDepth` 1 par défaut (`sa/index.ts:185-198`) ; au-delà du plafond, l'activation échoue en `ACTIVATION_LIMIT_REACHED` (`sa/activation.ts:24-31`) au lieu d'attendre : la file de L-10 est à écrire dans `qrg-router`. Un enfant natif ne peut demander aucune approbation (`sa/child-agent.ts:171-175, :229-234`).

**Registre et journal.** État durable par `ctx.storageDomain` (`packages/storage/storage-domain/src/spec.ts:15-60`, monté par `base.yml:187-190`, présent au tag) ; miroir dans la session racine par `appendPluginRecord(session, 'plugin:qrg/decision', data)` à master seulement, après déclaration du type dans `PluginRecordMap` (`packages/core/session/src/index.ts:468-470, :483-485`).

**Événements.** `subagent/start` et `subagent/end` portent fournisseur, identifiant, caractère local et raison d'arrêt, sans durée ni tokens (`sa/index.ts:158-166` ; `sa/types.ts:80-115`).

**Au tag.** Pas de `startActivation` mais `start(name, request)` et `startContinuable(spec)` (tag: `sa/index.ts:261, :559`), avec `persona` et `toolFilter`, sans `cwd` ni `agentPreset` ; même héritage de route (tag: `sa/child-agent.ts:69-71`) ; ni `appendPluginRecord`, ni paquet `worktree` sous `packages/experimental/`.

## `qrg-claude-code`

**Interface.** Un fournisseur implémente `SubagentProvider` : `name`, `capabilities` (`agentOptions`, `agentPreset`, `outputSchema`, `depthLimit`), `inheritsParentContext`, `agentRouteDefaults?`, `start` et `prepareContinuable` facultatifs mais au moins un des deux (`sa/types.ts:117-129, :313-356`). Il s'enregistre par `ctx.subagents.registerProvider` sous un nom unique (`DUPLICATE_PROVIDER`, `sa/index.ts:547-566`). Le service vérifie les capacités puis passe la requête telle quelle à `start` (`sa/index.ts:214-216, :631-651`). `prepareContinuable` ne rend qu'un amorçage d'historique pour un agent DSH local (`sa/types.ts:198-225`), inutilisable pour un processus externe.

**L'officiel.** `@deepseek-ai/dsh-subagent-claude-code` injecte `subagents` et `subprocess` ; sa `Config` compte `providerName`, `model`, `env`, `permissionMode` (défaut `dontAsk`) et `disposeGraceMs` (`cc/src/index.ts:30-66`) ; aucune capacité, aucun contexte hérité, `start` seul (`cc/src/index.ts:73-115`). `run.ts` (587 lignes, 893 pour tout `src`) construit une invite texte unique (`cc/src/run.ts:184-199`), un environnement expurgé (`:329`), `persistSession: false` (`:330`), interdit `AskUserQuestion` et en mode `plan` aussi `ExitPlanMode` (`:331-333`), fournit un `canUseTool` qui refuse sauf en `bypassPermissions` où il n'y en a pas (`:335-349`), décline `onElicitation` (`:351-359`), annule `onUserDialog` (`:360-368`) et ne garde que le texte du résultat (`:236-261`). Il ne passe ni `mcpServers`, ni `resume`, ni `settingSources` (`note-ps:29`).

**Ce que le fork doit ajouter, au-delà des callbacks.** D'abord la continuité : chaque relance est un nouveau `start` avec `resume`, et l'identifiant ne peut passer que par un service propre au fork, appelé par `qrg-router`, ou par un canal latéral indexé sur `request.parent` (`sa/types.ts:153`). Ensuite le modèle par décision : déclarer `agentOptions: true` et lire `request.agentOptions.model`, ou monter une instance par modèle, l'officiel fixant le modèle par instance (`cc/README.md:43`). Puis les modes : l'officiel n'offre que `dontAsk`, `acceptEdits`, `auto`, `plan` et `bypassPermissions` (`cc/src/run.ts:44-50`) ; le fork ajoute `default` et retire `bypassPermissions` du schéma. Puis l'usage : `SubagentResult` n'a pas de champ d'usage (`sa/types.ts:252-278`) ; le fork le lit dans le message de résultat (type `SDKResultMessage` déjà importé, `cc/src/run.ts:15` ; contenu non vérifié) et le publie pour `qrg-meter`. Enfin les questions : le fork ne peut pas appeler `ctx.userQuestions.ask` au nom de l'enfant (voir `qrg-ask`).

**Empaquetage.** À master, le bundle officiel insère aussi l'outil `subagent_claude_code`, ajouté « to every Agent as a global tool » (`cc/cordis.patch.yml:4-9` ; `cc/README.md:32`) ; au tag, seulement le fournisseur (tag: `cc/cordis.patch.yml:4-6`). Le bundle QRG n'insère que le fournisseur, et le lot 1 ne doit pas activer la couche officielle telle quelle. L'officiel accepte plusieurs instances de noms distincts (`cc/README.md:42`) : au lot 1, une instance par couple modèle et mode suffit pour le mode ponctuel.

**Identifiants.** L'environnement de l'enfant perd tout nom contenant `KEY`, `PASSWORD`, `SECRET` ou `TOKEN` et tous les `DSH_*` (`packages/subprocess/subprocess/src/index.ts:47, :66-80`) : un `ANTHROPIC_API_KEY` du parent n'atteint jamais Claude Code, sauf par `env` explicite. Hypothèse à tester : une connexion par abonnement stockée sous `HOME` fonctionne, une variable de jeton OAuth serait retirée.

**Tests.** `cc/tests/messages-fixture.ts` (224 lignes, MIT) sert `/v1/messages` sur 127.0.0.1 avec trois comportements, `complete`, `hold` et `tool-use` (`:4-12`) ; il en faudra un qui déclenche `AskUserQuestion`. `tests/` n'est pas publié (`cc/package.json:26-32`) : copier le fichier. `cc/tests/real-product.spec.ts` pilote un vrai `claude` avec une clé factice, `ANTHROPIC_BASE_URL` local, `HOME` isolé et télémétrie coupée (`:99, :170-184`) ; la règle « Aucune variable `ANTHROPIC_API_KEY` » du hand-off l'interdit en l'état.

**Homonymes.** Les paquets expérimentaux `@deepseek-ai/dsh-experimental-claude-code-mods` et `@deepseek-ai/dsh-hooks-claude-code` exécutent dans DSH des mods et des hooks écrits pour Claude Code (`packages/experimental/claude-code-mods/README.md:12` ; `packages/experimental/hooks-claude-code/README.md:12`, README lus seulement) : ils ne pilotent pas le processus Claude Code et ne remplacent pas le fork.

**Au tag.** Même `Config` et même SDK 0.3.263 (tag: `cc/package.json:44` ; master `:48`) ; `start` obligatoire et capacités `toolFilter` et `persona` à la place d'`agentPreset` (tag: `sa/out-of-process.ts:57-63`).

## `qrg-ask` et le serveur MCP `ask_user`

**Service natif.** `ctx.userQuestions.ask({questions, agent?, signal?})` (`uq/index.ts:287-339`) prend des questions à `id`, `question`, `header`, `options` (`label`, `description`) et `multiSelect`, et rend `{answers: [{id, selected, custom?}]}` (`uq/types.ts:37-69`), forme proche de celle d'`AskUserQuestion`. Il passe par le waterfall `user-questions/request` (`uq/types.ts:148-162`) ; le service est monté par la base (`base.yml:79-80`) et la carte web vient de `dsh-client-ui-user-questions` (`web.yml:451-452`).

**Contraintes.** Un agent non racine est refusé (`DELEGATED_CALLER`, `uq/index.ts:131-144`), règle documentée (`packages/interaction/tool-ask-user/README.md:74`). Sans `agent`, la requête ne part pas vers le navigateur : le relais hôte appelle `next()` (`packages/api/remotes/src/index.ts:64-65`) et l'appel échoue en `NO_PROVIDER` (`uq/index.ts:318-324`). Reste à poser la question au nom de la racine (`ctx.agents.roots()`, `packages/core/agent/src/index.ts:592-602`) : la carte s'affiche alors dans la session racine, et une carte sans `callId` n'est pas projetée, disparaît avec l'attente et ne survit pas à un redémarrage (`packages/client/ui-user-questions/src/client/index.ts:275-276`).

**Agents natifs : un outil Cordis plutôt qu'un serveur MCP.** L'enfant natif tourne dans le même processus : `qrg-ask` lui fournit un outil `ask_user` (ligne d'outils du preset choisi par `agentPreset`) qui appelle le relais directement. Pas de socket, et pas de délai imposé sauf si l'outil déclare `timeoutMs` (`packages/guard/timeout-policy/src/index.ts:57-59`), alors que le client MCP de DSH coupe à 60 s par défaut (`packages/mcp/mcp-client/src/index.ts:36-37`). DSH possède déjà pour la racine le schéma « attente bornée puis réponse tardive » : `ask_user_question` en mode `timed` (120 s par défaut, `packages/interaction/tool-ask-user/src/index.ts:15-26`) s'appuie sur `askTimed`, qui rend `{pending: true, callId}` à l'échéance (`uq/index.ts:234-269`), et la réponse tardive arrive comme message `user-question-reply` (`uq/index.ts:164-206`).

**Claude Code et ACP.** Pour Claude Code, `canUseTool` couvre `AskUserQuestion` et les autorisations ; un serveur MCP `ask_user` passé par `mcpServers` n'est utile que pour un outil explicite et pourrait tourner dans le processus du fournisseur (hypothèse sur le SDK). Pour ACP, aucune injection sans modifier DSH (`packages/subagent/subagent-acp/src/run.ts:489, :492`).

**Autorisations.** `ctx.approval.request` exige un tour ouvert (`packages/interaction/user-approval/src/index.ts:215-223`), rend `rejected` en politique `never` (`:275`) et n'a que quatre issues, `allowed-once`, `rejected`, `cancelled`, `unavailable` (`packages/interaction/user-approval/src/types.ts:32`). « Accepter avec modification » (Q-10) passe donc par une question, pas par ce service.

**Au tag.** `user-questions`, `tool-ask-user` et `user-approval` identiques.

## `qrg-meter`

**Forme.** Un paquet client déclare `"dsh": {"client": {"platform": "web", "inject": [...], "external": [...], "immediately": ...}}` (`packages/client/modules/src/client/manifest.ts:173-193`) et doit exporter `./client` (`packages/client/modules/src/index.ts:855-869`). Une entrée client inactive fait échouer tout le démarrage web (`packages/client/web/src/boot-client.ts:66-89`) : une injection manquante casse l'interface entière. **Emplacement.** Le slot `conversation.composer.dock` (« Ambient entries below the composer card », `packages/client/ui-conversation/src/client/contract/slots.ts:273-274`) porte déjà les pastilles `activity` (ordre 0) et `usage` (ordre 1), une par `id` « so a plugin replaces or adds a single pill by id » (`packages/client/ui-chat/src/client/apply.ts:321-330`). **Données.** Côté hôte, `ctx.sessionProjections.register` déclare une projection recalculée sur chaque événement validé de la session (`packages/session/session-projection/src/index.ts:40-44, :225-228`), lue côté client par `useProjection`. Pour C-05, qu'une projection voie les enregistrements de plugin est probable d'après `session-projection/src/index.ts:40-44`, non vérifié.

**Au tag.** Parseur du manifeste, démarrage et slots identiques ; le dock n'y a qu'une entrée `stats` ; `zod` et `react-virtual` n'y sont pas fournis par la plateforme.
